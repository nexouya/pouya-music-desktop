# Production-Ready Music Recommendation Engine Architecture

This document outlines the architecture, algorithms, formulas, database schema, and Node.js + PostgreSQL code examples for a multi-stage recommendation pipeline designed to support 100 million users, akin to Spotify or TikTok.

## Stage 1: Candidate Retrieval

The candidate retrieval stage narrows down millions of tracks to a subset (e.g., 500-1000 tracks) using multiple independent retrieval strategies.

*   **User Listening History:** Tracks the user recently listened to and enjoyed.
*   **Collaborative Filtering (Similar Users):** Uses Matrix Factorization (ALS) to find users with similar listening patterns and retrieves tracks they like.
*   **Embeddings (Similar Tracks):** Uses Approximate Nearest Neighbor (ANN) search on track embeddings (e.g., Word2Vec style Track2Vec) to find acoustically or contextually similar tracks.
*   **Similar Artists/Genres:** Expands candidates based on the user's top artists and genres.
*   **Trending & Viral Tracks:** Retrieves globally and locally trending tracks to inject cultural relevance.
*   **New Releases:** Tracks from followed artists or genres released in the last 7 days.

## Stage 2: User Profile (Real-Time State)

A continuously updated user profile tracks over 40 distinct interaction types. We maintain this as a feature vector.

**Tracked Signals:**
*   **Engagement:** Play, Skip, Fast Skip (<10s), Listen %, Completion Rate, Replay Count, Loop Count, Likes, Dislikes.
*   **Intent:** Search Queries, Playlist Add, Playlist Remove, Share Events, Download Events, Queue Changes.
*   **Context:** Session Duration, Time of Day, Day of Week, Device, Country, Language.
*   **Acoustic Preferences:** Tempo, Danceability, Energy, Acoustic, Instrumental, Explicit Content, Release Year.
*   **Behavioral:** Discover vs. Familiar Ratio, Artist/Genre Diversity, Listening Streak.

## Stage 3: Dynamic Scoring

Every candidate from Stage 1 is scored using a sophisticated multi-objective ranking model.

**Scoring Formula (Simplified Unified Score):**
`Score = w1 * P(Listen) + w2 * P(Finish) + w3 * P(Replay) + w4 * P(Like) + w5 * P(Playlist Add) - w6 * P(Skip)`

Where `P(Event)` is the predicted probability of the event occurring, generated by a Deep Neural Network (DNN).

## Stage 4: Machine Learning

**Embeddings Generation:**
*   **Track2Vec:** Treats user listening sessions as "sentences" and tracks as "words". Uses Skip-Gram to generate embeddings where tracks frequently listened to together are close in vector space.
*   **Audio Embeddings:** Extracts features using CNNs on the audio spectrogram (capturing tempo, key, timbre).

**Model Architecture:**
A Two-Tower Neural Network or DeepFM model is used.
*   **Tower 1 (User):** Embeds the user profile, context, and historical features.
*   **Tower 2 (Item):** Embeds the track features, artist, genre, and acoustic data.
*   The dot product of the two towers produces the final relevance score, which is passed through logistic regression layers to predict `P(Listen)`, `P(Finish)`, etc.

## Stage 5: Exploration

To prevent the "filter bubble", we use **Contextual Bandits (e.g., Upper Confidence Bound - UCB)**.
*   10-20% of the feed is reserved for exploration.
*   The system intentionally serves highly uncertain candidates (e.g., new artists, adjacent genres) and updates the model based on the user's reaction.

## Stage 6: Re-ranking

The final ranked list is passed through a deterministic re-ranking filter (like Maximal Marginal Relevance - MMR) to ensure diversity.

*   **Penalties:** Applies negative weights if the same artist, album, or genre appears consecutively.
*   **Fatigue Rules:** Drops tracks the user has listened to >3 times in the last 24 hours unless explicitly requested.

## Stage 7: Online Learning

*   Stream processing (e.g., Apache Kafka + Flink) captures every micro-interaction (skip, replay).
*   User feature vectors (stored in Redis) are updated in real-time.
*   The DNN models are periodically fine-tuned (incremental learning) to adapt to shifting global trends.

## Stage 8: Database Design (PostgreSQL)

For structured metadata and historical truth. (Note: In production at 100M scale, Cassandra/ScyllaDB is preferred for interactions, but PostgreSQL is perfect for core entities).

```sql
-- Core Entities
CREATE TABLE users (
    id UUID PRIMARY KEY,
    username VARCHAR(255) NOT NULL,
    country VARCHAR(2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE artists (
    id UUID PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    popularity INT DEFAULT 0
);

CREATE TABLE tracks (
    id UUID PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    artist_id UUID REFERENCES artists(id),
    duration_ms INT NOT NULL,
    release_date DATE,
    tempo FLOAT,
    energy FLOAT,
    danceability FLOAT,
    popularity INT DEFAULT 0
);

-- Interactions (Partitioned by date in production)
CREATE TABLE interactions (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID REFERENCES users(id),
    track_id UUID REFERENCES tracks(id),
    interaction_type VARCHAR(50) NOT NULL, -- 'PLAY', 'SKIP', 'LIKE', 'SHARE'
    listen_duration_ms INT,
    context VARCHAR(50), -- 'EXPLORE', 'PLAYLIST', 'SEARCH'
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_interactions_user_track ON interactions(user_id, track_id);

-- Features & Embeddings (Using pgvector for ANN search)
CREATE EXTENSION vector;

CREATE TABLE track_embeddings (
    track_id UUID REFERENCES tracks(id) PRIMARY KEY,
    embedding vector(128) -- 128-dimensional embedding
);
CREATE INDEX ON track_embeddings USING ivfflat (embedding vector_cosine_ops);

CREATE TABLE user_features (
    user_id UUID REFERENCES users(id) PRIMARY KEY,
    taste_profile JSONB,
    recent_history UUID[],
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## Stage 9 & 10: Performance, APIs & Code Example (Node.js)

To support 100M users:
1.  **Caching:** Redis stores real-time user profiles and pre-computed candidate pools.
2.  **ANN Search:** Vector databases (Milvus, Pinecone, or PostgreSQL with `pgvector`) handle similar track retrieval in milliseconds.
3.  **Microservices:** Split into `Candidate Retrieval Service` (Go/Rust for speed), `Ranking Service` (Python/TensorFlow), and `API Gateway` (Node.js).

### Node.js REST API Example

```javascript
// server.js (Express + pg + redis)
const express = require('express');
const { Pool } = require('pg');
const Redis = require('ioredis');

const app = express();
const pgPool = new Pool({ connectionString: process.env.DATABASE_URL });
const redis = new Redis(process.env.REDIS_URL);

app.use(express.json());

// 1. Get Recommendations API
app.get('/api/v1/recommendations', async (req, res) => {
    const userId = req.query.user_id;
    const limit = parseInt(req.query.limit) || 20;

    try {
        // Step 1: Check Redis cache for pre-computed personalized candidates
        const cacheKey = `recs:user:${userId}`;
        const cachedRecs = await redis.get(cacheKey);
        
        if (cachedRecs) {
            return res.json({ source: 'cache', tracks: JSON.parse(cachedRecs).slice(0, limit) });
        }

        // Step 2: Fallback to real-time retrieval & ranking (Simplified for example)
        // Retrieve user features
        const userRes = await pgPool.query('SELECT taste_profile FROM user_features WHERE user_id = $1', [userId]);
        const tasteProfile = userRes.rows[0]?.taste_profile || {};

        // Retrieve candidates (e.g., using pgvector for tracks similar to user's favorite)
        // In reality, this calls a dedicated Candidate Retrieval Microservice
        const topGenre = tasteProfile.top_genre || 'Pop';
        const candidateRes = await pgPool.query(`
            SELECT t.id, t.title, t.artist_id, t.tempo, t.energy, t.popularity
            FROM tracks t
            WHERE t.popularity > 50
            LIMIT 200
        `);

        // Step 3: Dynamic Scoring (Simplified logic in JS, normally calls ML Service)
        const candidates = candidateRes.rows.map(track => {
            // Apply Stage 3 Scoring Formulas
            let score = track.popularity * 0.1;
            if (Math.abs(track.energy - (tasteProfile.preferred_energy || 0.5)) < 0.2) score += 50;
            return { ...track, score };
        });

        // Step 4: Re-ranking & Diversity Sorting
        candidates.sort((a, b) => b.score - a.score);
        
        const finalRecs = applyDiversityFilter(candidates).slice(0, limit);

        // Async Cache update
        redis.set(cacheKey, JSON.stringify(finalRecs), 'EX', 300); // 5 minute TTL

        res.json({ source: 'computed', tracks: finalRecs });
    } catch (err) {
        console.error(err);
        res.status(500).json({ error: 'Internal Server Error' });
    }
});

// 2. Real-Time Interaction Ingestion API
app.post('/api/v1/interactions', async (req, res) => {
    const { userId, trackId, type, listenDuration } = req.body;
    
    try {
        // Fast insert to PostgreSQL (or Kafka stream in production)
        await pgPool.query(`
            INSERT INTO interactions (user_id, track_id, interaction_type, listen_duration_ms)
            VALUES ($1, $2, $3, $4)
        `, [userId, trackId, type, listenDuration]);

        // Real-time user profile update in Redis
        const userKey = `profile:user:${userId}`;
        if (type === 'SKIP') {
            await redis.hincrby(userKey, 'total_skips', 1);
        } else if (type === 'PLAY' && listenDuration > 30000) {
            await redis.hincrby(userKey, 'total_plays', 1);
        }

        // Invalidate recommendation cache so next fetch gets fresh data
        await redis.del(`recs:user:${userId}`);

        res.status(202).send('Interaction registered');
    } catch (err) {
        res.status(500).send('Error registering interaction');
    }
});

// Helper: Stage 6 MMR Diversity Filter
function applyDiversityFilter(rankedTracks) {
    const selected = [];
    const seenArtists = new Set();
    
    for (const track of rankedTracks) {
        if (!seenArtists.has(track.artist_id)) {
            selected.push(track);
            seenArtists.add(track.artist_id);
        } else {
            // Artist already seen, heavily penalize or skip
            // In a real MMR algorithm, we re-evaluate distances here
        }
    }
    return selected;
}

app.listen(3000, () => console.log('Recommendation Service running on port 3000'));
```
